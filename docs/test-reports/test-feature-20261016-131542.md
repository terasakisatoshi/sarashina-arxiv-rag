## Per-Feature Details

### chat + translate (first-time CLI onboarding)
- **Role:** Developer with moderate Python/CLI experience, new to this project, reads only the published README.
- **Use Case:** Set up the project and run the `chat` and `translate` commands shown in the README.
- **What they tried:** Followed the README setup (`uv sync`, write `.env`), then ran the documented `chat` and `translate` invocations with the documented flags.
- **Discoverability:** Partial. The command forms, flags, defaults, and language-resolution rules are fully recoverable from the README. What is missing: there is **no source-acquisition step** — no `git clone`, no `uv tool install`, no package name / PyPI reference. `uv sync` (README line 15) silently assumes the reader already has the checkout. A true first-timer cannot start.
- **Setup:** Works as described once you have the source. `uv sync` installs dependencies; the CLI reads `SARASHINA_API_KEY` from a project-root `.env`.
- **Functionality:** Verified via the external-downstream gate (see Blind-Mode Findings): the package installs from the local checkout into a fresh Python 3.14 venv, all four console scripts register, every documented flag/alias is present in `--help`, and both CLIs fail gracefully with a clear message when no key is set. The live API round-trip was not run (network + real secret → blocked precondition). The full offline suite (`uv run pytest`) passes 48/48.
- **Expected vs Actual Outcome:** Partially met. The commands and flags are accurate and runnable; the "docs alone are enough to install" half of the expected outcome is not satisfied because installation from scratch is undocumented.
- **Blocked steps:** The documented `chat`/`translate` calls were not executed end-to-end: they require outbound network access to `api.sarashina.ai` and a real `SARASHINA_API_KEY`. Per the safety rules, that branch was reported rather than run. Build/entry-point/argument handling was exercised instead.
- **Friction points:**
  - No source-acquisition instruction (biggest gap).
  - No expected stdout shown for `chat` or `translate`, so success is unverifiable from docs.
  - The `.env` working directory is only described as "プロジェクト直下"; the cwd from which the CLIs must be run is never stated (it matters — `load_dotenv(".env")` is cwd-relative).
  - `-t/--temperature` default is undocumented (source default is `None`; the field is omitted from the request payload entirely, not `0`).
  - No `--from` example (only `--to`), and Python 3.14 provisioning is not explained.
- **Doc suggestions:** Add a "get the source" step; show one expected-output sample per CLI; state that the CLIs must run from the directory containing `.env`; document the `-t` default; add a `--from` example.

## Expected vs Actual Outcome

The expected outcome (docs alone suffice to install, configure, and run the CLIs) is **partially achieved**. Configuration and command usage are documented accurately and verified working. The install half is incomplete: the README assumes an existing checkout and never says how to obtain it. The most surprising/actionable finding is that the README's own setup snippet (`echo 'SARASHINA_API_KEY=...' > .env`) is destructive if the reader already has a `.env` — this matches a known past incident noted in the repo's `AGENTS.md` (a previous `> .env` destroyed the user's key).

## Issues Found

Ordered by severity:

1. **(High, docs) No source-acquisition / install-from-scratch step.** README jumps straight to `uv sync`; a first-time user cannot obtain the project from the docs. — README §セットアップ lines 10–16.
2. **(High, docs) Destructive setup snippet.** `echo 'SARASHINA_API_KEY=your_api_key_here' > .env` (README line 22) silently truncates an existing `.env` and its real key. The repo's own `AGENTS.md` records that this exact mistake previously destroyed the user's API key.
3. **(Medium, docs) No expected output** for any `chat`/`translate` example — success cannot be judged from docs.
4. **(Medium, docs) cwd requirement unstated.** `.env` is loaded cwd-relative, but the README never says the CLIs must be invoked from the project root.
5. **(Low, docs) `-t/--temperature` default undocumented**, and no `--from` example.

## Blind-Mode Findings

**Doc surface handed to the doer:** a scratch directory containing only `README.md` (128 lines) — the sole user-facing doc. Source, `pyproject.toml`, git history, and tests were excluded.

**From-docs program + manifest (doer output, with GAP markers):**
- `onboarding.sh` — a shell script of the README's literal commands, with `# GAP:` markers for: missing source-acquisition; unknown required cwd; Python 3.14 provisioning; quoting/verification of the key; no expected stdout; undocumented `-t` default; no `--from` example.
- `pyproject.toml` — all-GAP placeholder manifest: `name`, `version`, `dependencies`, and `[project.scripts]` targets are all `GAP:` because the README shows no manifest. Only `requires-python = ">=3.14"` is doc-backed.

**Verification-gate commands + verbatim results:** (throwaway downstream dir outside the workspace, resolving the doer's source-acquisition gap to the local checkout)

```
$ uv venv --python 3.14 <down>/.venv            # CPython 3.14.4
$ uv pip install /Users/terasaki/.../sarashina-client
  + sarashina-client==0.1.0 (from file:///.../sarashina-client)
  ... (fastapi, markdown, pymupdf, python-dotenv, uvicorn, ...)
$ <down>/.venv/bin/chat --help       -> rc=0   OK
$ <down>/.venv/bin/translate --help  -> rc=0   OK
$ env -u SARASHINA_API_KEY <bin>/chat "..."        -> "error: SARASHINA_API_KEY is not set" rc=1
$ env -u SARASHINA_API_KEY <bin>/translate "..." --to en -> same error rc=1
$ uv run pytest -q                   -> 48 passed
```

**Source-checked verdict (orchestrator):** The doer's inferred API facts are all correct — `chat`/`translate` exist, flags/aliases match `--help`, `chat -m` default is `sarashina3-mini`. The gate passes: package builds and installs as an external dependency, entry points and documented flags resolve, offline suite is green.

**Misleading-doc findings (refuted/downgraded candidates → signposts):**
- The doer produced an all-GAP `pyproject.toml`. This is **not** a doer error: the README genuinely never shows a manifest or install target. Signpost — add a one-line "clone the repo, then `uv sync`" step so the manifest doesn't need documenting inline.
- The doer's setup script writes a placeholder key with `> .env`, faithfully copied from README line 22. The doc leads a careful reader straight into destroying an existing `.env`. Signpost — change the README to instruct appending/editing (e.g. `[ -f .env ] || echo ... > .env`) and warn against overwriting.
- The doer flagged the `-t` default as unknown; this is a **valid** doc gap (source default is `None`, not a number). Signpost — state the default explicitly.

**Pure rejects:** none. Every doer candidate was doc-grounded.

## Suggestions

Ordered by impact:

1. Add an explicit "obtain the source" step before `uv sync` (clone URL or `uv tool install`), so onboarding works from scratch.
2. Make the `.env` instruction non-destructive — never `>` an existing `.env`; echo only if absent, or edit instead. Add a warning, mirroring the `AGENTS.md` note.
3. Show one expected `stdout` sample for `chat` and for `translate`.
4. State the required cwd (project root, where `.env` lives).
5. Document the `-t/--temperature` default and add a `--from` example.
